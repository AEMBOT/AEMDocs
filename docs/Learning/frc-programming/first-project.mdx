## Exploring the current setup.
We're using this template because it's quite barebones, just containing the necessary files for WPILib and AdvantageKit with a bit
of boilerplate. From here, we'll set up a basic **command based** codebase.

Depending on your experience with programming, your first instinct exploring this codebase might be to look in `Main.java`, which you may be
surprised to find relatively empty. Indeed, the main class only really serves to start WPILib, which will handle our overall execution flow
from there:
```java
public static void main(String... args) {
  RobotBase.startRobot(Robot::new);
}
```

The `Robot` class used in the above function is, of course, defined in `Robot.java`, which will have a lot more going on. The `Robot` class
is, in a simple robot, the primary class that orchestrates our robot code. At the moment, it mainly contains boilerplate; all the code currently
does is set up AdvantageKit logging.

Aside from those, `Constants.java` is, as the name implies, a final class containing nothing but constant values. `BuildConstants.java` is similar,
but it's automatically generated every time you build robot code; it serves to store information about the current build such as the Git commit and
the date at which it was built.

## Iterative robot code
The most basic way to write robot code is with an iterative approach. In this structure, we explicitly write the step-by-step code that will be executed
every loop. As an example, look at the `teleopPeriodic` method in `Robot`. As stated by the JavaDoc _(the multiline comment above the method header)_,
code in this method will be run every loop (at 50Hz) while the robot is enabled and in the teleoperated state (drivers have control of the robot). 

In fully iterative robot code, we might write something that looks similar to this to control a simple robot:
```java
@Override
public void teleopPeriodic() {
  drivetrain.driveManual(driverController.getLeftY(), driverController.getRightY());

  if (driverController.getRightTriggerAxis() > 0.5) { // XBOX controller triggers are analog (0.0-1.0)
    intake.run();
    indexer.run();
    shooter.shoot();
  } else if (driverController.getBButton()) {
    intake.runReverse();
    indexer.runReverse();
    shooter.idle();
  } else {
    intake.stop();
    indexer.stop();
    shooter.idle();
  }
} 
```

For a more immediate example, try adding the following line to your `teleopPeriodic` function in `Robot.java`:
```java
System.out.println("I am on the " + DriverStation.getAlliance().get().name() + " alliance!");
```

Indeed, it is very easy to get started with iterative robot programming. However, once your programming becomes more complicated,
an iterative codebase can quickly become very spaghetti-fied. 

For a more complex example, let's say we have a simple pick-and-place robot that needs to orchestrate motions of a pivot, an elevator, and a wrist. 
It needs three poses: grabbing game pieces, holding itself within frame perimeter, and placing game pieces. It needs to go into its standby pose between
each grabbing and placing, and it needs to move each component in such a sequence that they won't collide with things. If we follow the same structure as before, 
our code might look something like this:
```java
public class Robot extends LoggedRobot {
  private enum ArmState {
    GRABBING(80, 0.5, 20),
    STANDBY(0, 0, 0),
    PLACING(10, 2, 90);

    public final double pivotAngleDeg;
    public final double elevatorHeightM;
    public final double wristPitchDeg;

    private ArmState(double pivotDegrees, double elevatorMeters, double wristDegrees) {
      this.pivotAngleDeg = pivotDegrees;
      this.elevatorHeightM = elevatorMeters;
      this.wristPitchDeg = wristDegrees;
    }
  }

  /** The arm state we are at or are changing from. */
  private ArmState previousArmState = ArmState.STANDBY;
  /** The arm state we are switching to. */
  private ArmState targetArmState = ArmState.STANDBY;

  private XboxController driverController = new XboxController(0);

  /* We'd define the subsystems (pivot, elevator, wrist) here as well */

  public Robot() {
    /* AdvantageKit setup would go here */
  }

  /** This function is called periodically during operator control. */
  @Override
  public void teleopPeriodic() {
    drivetrain.driveManual(driverController.getLeftY(), driverController.getRightY());

    if (driverController.getAButtonPressed()) {
      targetArmState = ArmState.PLACING;
    } else if (driverController.getBButtonPressed()) {
      targetArmState = ArmState.STANDBY;
    } else if (driverController.getYButtonPressed()) {
      targetArmState = ArmState.PLACING;
    }

    moveArm();
  }

  /** Run once per periodic loop. Moves the arm to {@link #targetArmState}. */
  private void moveArm() {
    if (previousArmState != targetArmState) {
      if (
        // If we're moving the arm from standby to an outward pose
        previousArmState == ArmState.STANDBY && targetArmState == ArmState.GRABBING
        ||
        previousArmState == ArmState.STANDBY && targetArmState == ArmState.PLACING
      ) {
        moveArmOutToState(targetArmState);
      } else if (
        // If we're moving the arm from an outward pose to standby
        previousArmState == ArmState.GRABBING && targetArmState == ArmState.STANDBY
        ||
        previousArmState == ArmState.PLACING && targetArmState == ArmState.STANDBY
        // If we're moving the arm from an outward pose to another outward pose,
        // we need to move to standby in between.
        ||
        previousArmState == ArmState.PLACING && targetArmState == ArmState.GRABBING
        ||
        previousArmState == ArmState.GRABBING && targetArmState == ArmState.PLACING
      ) {
        moveArmInToState(ArmState.STANDBY);
      }
    }
  }

  /**
   * Moves the arm to the given state in the order of pivot, elevator, wrist
   * @return Whether or not we've reached the given state.
   */
  private boolean moveArmOutToState(ArmState state) {
    pivot.setTarget(state.pivotAngleDeg);
    if (pivot.withinTolerance()) {
      elevator.setTarget(state.elevatorHeightM);
      if (elevator.withinTolerance()) {
        wrist.setTarget(state.wristPitchDeg);
        if (wrist.withinTolerance()) {
          previousArmState = state;
          return true;
        };
      }
    }
    
    return false;
  }

  /**
   * Moves the arm to the given state in the order of wrist, elevator, pivot.
   * @return Whether or not we've reached the given state.
   */
  private boolean moveArmInToState(ArmState state) {
    wrist.setTarget(state.wristPitchDeg);
    if (wrist.withinTolerance()) {
      elevator.setTarget(state.elevatorHeightM);
      if (elevator.withinTolerance()) {
        pivot.setTarget(state.pivotAngleDeg);
        if (pivot.withinTolerance()) {
          previousArmState = state;
          return true;
        }
      }
    }

    return false;
  }
}
```

This is unpleasant, to say the least. And this is only for a very simple system! Imagine if we had to move the pivot multiple times within
a transition; or if we needed more complex timing to run our intake or claw; or, heavens forbid, if we needed to choreograph an entire
autonomous routine this way!

Of course, we _could_ make this better. We could, as the great programmers before us have done, create abstraction upon abstraction,
layer upon layer, until all of this pain is buried and our higher-level code is clean as can be. But we don't have to, because the 
folks behind WPILib have already done so for us.

## Command based robot code
A **command** is, in essence, an object that contains:
- Some code to be run (a **runnable** object, or a **lambda**)
- Instructions for _how_ it should be run. For example, an `InstantCommand` will have its code run only once, whereas
  a `RunCommand` will have its code run repeatedly (once per periodic loop) until the command is told to end.

To actually use these commands, we have the **command scheduler**, which runs on the robot's periodic loop and handles executing our scheduled
commands.
